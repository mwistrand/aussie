# End-to-End Test Suite

The e2e suite boots a full gateway stack (Aussie + demo + Cassandra + Redis) in
Docker via Testcontainers, registers the demo service through the admin API,
then runs HTTP-level tests against the gateway. It is intentionally separate
from `:check` because container boot is slow and requires Docker.

## Prerequisites

- Docker daemon reachable (Docker Desktop, Colima, etc.)
- `npm` on `PATH` (used by the `demo-deps` target to install the demo's
  dependencies the first time)

## Running

```shell
make e2e
```

For repeated packaged-artifact lifecycle checks, use:

```shell
make e2e-soak SOAK_RUNS=3
```

The scheduled CI resilience lane uses this target. Each run creates a fresh
gateway/dependency stack, exercises the restart and replica lifecycle tests,
and tears the stack down before the next run.

The `e2e` target depends on `demo-deps`, which installs the demo's Node
dependencies via `npm ci` (or `npm install` on a fresh clone without a
lockfile). Subsequent runs skip the install step.

To view the most recent run's container logs:

```shell
make e2e-logs
```

Logs land under `api/build/e2e-logs/<timestamp>/` (one file per container).
They are written on test failure and on bootstrap failure; passing runs do not
emit them. A bootstrap failure also writes a Java stack trace to
`api/build/e2e-logs/bootstrap-<timestamp>/bootstrap-failure.txt`.

## What the suite does

`SuiteBootstrapListener` (a JUnit Platform `LauncherSessionListener`) runs once
per test JVM:

1. Starts Cassandra, Redis, the demo, and the API container on a shared Docker
   network with aliases `cassandra`, `redis`, `demo`, `api`.
2. Lets the API apply the ordered, checksummed Cassandra migration manifest
   before bootstrap and the other startup observers run.
3. Registers the demo service through `POST /admin/services` using a per-run
   bootstrap key (`AUSSIE_BOOTSTRAP_KEY`), overwriting `baseUrl` to the
   in-network hostname.
4. Publishes a `SuiteContext` that test classes read for the gateway URL, demo
   URL, bootstrap key, the demo's `serviceId`, and the Cassandra host and port.

The suite assumes a single forked JVM (`maxParallelForks = 1`, `forkEvery = 0`)
because the singleton harness is not safe to share across forks.

The lifecycle lane restarts the packaged gateway three times while retaining
the shared Cassandra/Redis dependencies. After each restart it waits for
readiness and sends repeated routed health requests, catching lost route state
and restart/readiness regressions without relying on developer-local services.

It also starts a second packaged gateway against the same Cassandra/Redis
network, verifies that it loads the existing route snapshot, stops the first
instance, and continues routed requests through the replica before restoring
the suite's original instance.

## Demo test API

When the demo runs under the e2e harness, it exposes a small state-mutation
API under `/__test__/*` so tests can inspect captured request metadata, inject
one-shot failures on specific routes, or stall a route by a fixed delay.

This surface is gated by two env vars:

| Variable | Purpose |
| --- | --- |
| `DEMO_TEST_API_ENABLED=true` | Enables the `/__test__/*` routes at all. |
| `DEMO_TEST_API_TOKEN=<random>` | Per-run shared secret. Callers must echo it in the `X-Test-Auth` header. Empty token refuses all `/__test__/*` requests. |

The harness sets both with values generated by `SecureRandom` at JVM start.
Captured request headers are projected through an allowlist before storage —
`Authorization`, `Cookie`, and other credentials are not retained.

> **Never set `DEMO_TEST_API_ENABLED=true` in a non-test deployment.** Even
> with the token gate, the surface exists to mutate demo behaviour and exists
> only for the harness's benefit.

## Environment variables consumed by the harness

The harness wires these into the API container; values without "harness-set"
in the description must be configured outside the harness if you reuse this
image elsewhere.

| Variable | Description |
| --- | --- |
| `QUARKUS_PROFILE` | Forced to `dev` (harness-set). |
| `CASSANDRA_CONTACT_POINTS` | `cassandra:9042` (harness-set). |
| `QUARKUS_REDIS_HOSTS` | `redis://redis:6379` (harness-set). |
| `DEMO_APP_URL` | `http://demo:3000` (harness-set). |
| `AUSSIE_BOOTSTRAP_ENABLED` | `true`. |
| `AUSSIE_BOOTSTRAP_KEY` | Random per-run, used as the bearer for service registration. |
| `AUSSIE_JWS_SIGNING_KEY` | Per-run 2048-bit RSA private key, base64-encoded in PKCS#8 format. |
| `AUSSIE_AUTH_ROUTE_AUTH_ENABLED` | `false` so the bootstrap key isn't interpreted as a JWT. Per-test overrides flip this on. |
| `CASSANDRA_RUN_MIGRATIONS` | `true`; the API applies migrations during startup. |

## Adding tests

Tests live under `api/src/e2eTest/java/aussie/e2e/`. Pull suite-scoped values
from `SuiteContext.get()`:

```java
var ctx = SuiteContext.get();
given().baseUri(ctx.gatewayBaseUri().toString())
        .when()
        .get("/{serviceId}/api/health", ctx.demoServiceId())
        .then()
        .statusCode(200);
```

JUnit 5 only; `org.junit.jupiter.api.Assertions` for assertions. Rest-assured's
own matcher DSL (which uses Hamcrest under the hood) is acceptable for response
body assertions.
